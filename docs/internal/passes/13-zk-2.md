## What it found

- The sweep runner's own liveness probe could report false green two ways: it accepted any HTTP response (so another project's dev server squatting the port read as "alive"), and it treated any exit code outside {0,1,2,124} as ok — fifteen suites had been silently running against a dead port. {cite: notes/reports/REPORT-Z2.md > "/verify — CLOSED: four consecutive clean sweeps (2026-09-05)"}
- The device pins file lives inside a OneDrive-synced folder, and the sync client briefly holding the file open caused `EPERM` rename failures on every tick, label read and proof — fixed with retry-with-backoff and an in-place-write fallback. {cite: notes/reports/REPORT-Z2.md > "Gate 0 — iteration 2 (serialized ticks)"}
- A forced label-refresh tick that arrived while a scheduled tick was mid-flight was silently dropped, leaving the live universe with no snapshot at read time; fixed by serializing ticks on a promise chain. {cite: notes/reports/REPORT-Z2.md > "Gate 0 — iteration 1 (rebuilt bundle, supervised validator, 3 s test cadence)"}
- A test-suite grep had been silently vacuous across two iterations because it piped through `2>/dev/null` under cmd.exe, which cannot resolve that redirection, so "nothing missing" meant "nothing ran" rather than a real clean result. {cite: notes/reports/REPORT-Z2.md > "Gate 1 — every reputation read proof-mediated under zk"}
- The pass's own review of the block-write path found a signal before any external reviewer did: a device fanned a block out as one row per own persona in a single burst, with adjacent rowids and identical timestamps — fixed to one row per action, shared across siblings only at read time. {cite: notes/reports/REPORT-Z2.md > "Gate 2 — migration 006: the validator stops knowing persona → root"}
- Adversarial review found `envelope_counters.counter` was `Date.now()`, letting an operator join persona, device and root purely from timestamps in the database; fixed with a device-persisted monotonic counter and hour-grain timestamps everywhere persona-addressed. {cite: notes/reports/REPORT-Z2.md > "Gate 4 — linkage test v2 + three adversarial reviews"}
- Adversarial review found the fork's vault record was addressed by the old persona's id in the clear, so an operator could see "old persona forked at time t" beside the new persona's continuity claim; fixed by sealing it as one opaque record. {cite: notes/reports/REPORT-Z2.md > "Gate 4 — linkage test v2 + three adversarial reviews"}
- The reviewers concluded "the validator stops knowing" held for the schema but not yet for traffic and addresses: the device enumerated its own roster to the validator on every render (one signed read per own persona), fixed to a single map read. {cite: notes/reports/REPORT-Z2.md > "Gate 4 — linkage test v2 + three adversarial reviews"}
- Population drift broke a fixture-only test during the marathon: with 83% of the seeded population at zero reputation, any positive score landed in the top decile, collapsing the decile model; fixed by computing deciles only over accounts with reputation, matching what the model always intended (no rep = tier 1 by definition). {cite: notes/reports/REPORT-Z2.md > "/verify — the closing sweeps, on the Gate 4 build"}
- One closing-sweep stop traced to a session-setup false alarm, not a linkage: the harness's own scheduled tick had already proved and submitted an identical fork claim moments before the test's dev-enqueued copy, so the validator's correct "replay" response was misread as a failure. {cite: notes/reports/REPORT-Z2.md > "/verify — the closing sweeps, on the Gate 4 build"}

## Judgment calls

- The preparation burst is still identified at render time by design: the feed's own eligibility read is the gate's data, read when the feed renders, and the operator already sees the render — so this residual isn't treated as a new leak to close. {cite: notes/reports/REPORT-Z2.md > "GATE 0 — the cheap residuals from Pass 1's rebuttal"}
- A dev-only rig (`POST /zk/dev/split-view`) was added specifically to make the anonymous history viewpoint lie, so the refusal-on-fork behavior is provable rather than merely claimed. {cite: notes/reports/REPORT-Z2.md > "GATE 0 — the cheap residuals from Pass 1's rebuttal"}
- The discovery fallback rule (`fallback=policy`) was deliberately kept reading the legacy tier, so the legacy discovery feed stays byte-for-byte unchanged while every other surface moved to proof-mediated tiers. {cite: notes/reports/REPORT-Z2.md > "Gate 1 — every reputation read proof-mediated under zk"}
- Old root-level block pairs were kept in a `blocks_legacy_export` table read by nothing but the down-migration, honoring the project's rule of no deletion without a rollback. {cite: notes/reports/REPORT-Z2.md > "Gate 2 — migration 006: the validator stops knowing persona → root"}
- Where a reviewer's finding was accepted as correct but not fixed — the fork-continuity proof is a tier proof with a label, not an in-circuit binding to the old persona's root — the documentation was rewritten to call the fork claim a vouch rather than a proof of the underlying relation. {cite: notes/reports/REPORT-Z2.md > "Gate 4 — linkage test v2 + three adversarial reviews"}
