# CROSS-DEPLOYMENT FRIEND WHITELIST ("Show my personas to a friend") — BUILD-READY SPEC
Read-only research on the working tree as of 2026-10-08 (HEAD 8359c79 + uncommitted overnight builds). Nothing was edited, built, started or deployed. Every primitive and reused function below was checked on disk at the cited file:line.

## 0. Verdict and shape

Build the dead drop exactly as dx-critic.txt WHITELIST describes, with these settled details: one envelope format (HPKE PSK mode, fixed 2 KiB plaintext, 4128-hex ciphertext) used by three readers (a paired Layers device, a link-only /d card, and later X porting); a validator table with five columns and three token-gated or open routes; a 1-hour re-seal publisher on the owner service that pads the envelope count to buckets of four; a friend device that fetches the whole drop on the existing uniform prefetch tick and trial-opens with a 2-byte PRF hint so the per-tick cost stays in the milliseconds; a FID-keyed merge seam at the two places cast authors are already assembled. v1 tiers are per-friend subject lists plus named presets. v1 is deniable (no persona signatures). Everything that fails, fails toward LESS disclosure.

Why this shape and not a route on the owner service: the owner app's middleware exempts only exact paths (middleware.ts:337-355) and the passphrase is the account (SECURITY-POSTURE §18); a friend-facing route there would be an ungated parser on the seed-holding process. The public validator already serves unauthenticated fetch-all reads (validator/zk.js:1067-1086 GET /zk/anon-casts) and CORS * (validator/server.js:85-90).

## 2. The envelope (lib/disclosure/envelope.ts — pure, isomorphic: device, owner server, /d page, tests)

Suite: `new CipherSuite({ kem: new DhkemX25519HkdfSha256(), kdf: new HkdfSha256(), aead: new Aes256Gcm() })` (identical to rootlink.ts:20). INFO = utf8("layers-disclosure/envelope/v1"). Mode PSK: `psk = { id: addrIdBytes(16), key: psk(32) }`.

Statement (plaintext JSON, then padded):
```
{ v: 1, addrId: hex16, seq: int>=0, issuedAt: ms, expiresAt: ms,
  subjects: [{ fid: int>0, fname: string(<=64, fname or .eth rule), display: string(<=48), kind: "main"|"persona" }] (1..8),
  label: string(<=48)   // how the owner wants to be named on the friend's card
  pad: string }         // spaces, so utf8 length === PLAINTEXT_BYTES
```
Constants: PLAINTEXT_BYTES = 2048 (8 subjects at ~120 bytes each plus header fit with margin; a statement that does not fit is REFUSED at seal time, never truncated). ct = AES-256-GCM over 2048 bytes = 2064 bytes → CT_HEX_LEN = 4128. enc = 32-byte X25519 encapsulation → 64 hex. Row id = 16 random bytes (32 hex). Delete token = 32 random bytes (64 hex); del_hash = sha256(token) hex.

Hint (trial-open accelerator): `hint = hex(hkdfSha256(ikm = psk, salt = encBytes, info = "layers-disclosure/hint/v1", 2))` (4 hex). The operator cannot compute it without the PSK; enc is fresh per envelope, so hints never link one recipient's envelopes across generations. A device checks 1 HKDF per (address,row) and does the X25519 only on a hint match (1/65536 false positives, harmless). Without the hint, 32 addresses × 512 rows = 16k WebCrypto X25519 ops per tick; with it, ~16k HKDFs (milliseconds).

Dummy rows (count padding): a real ephemeral keypair's serialized public key as enc, 2064 random bytes as ct, 4 random hex as hint, a fresh token and the same expiry window. Indistinguishable by construction.

addrId = sha256("layers-disclosure/addr/v1|" + pkHex).slice(0, 32). The PSK id in the key schedule is the addrId bytes, so an envelope sealed for address A fails to open under address B even if the PSK leaked between them.

Address string (what the friend hands the owner): `LD1.` + base64url(addrId(16) || pk(32) || psk(32)) (107 chars). Also offered as a link `https://<public app>/d/pair#LD1....` (the fragment never reaches a server) and as a QR.

Link-friend key (plain Farcaster users): key = 32 random bytes (generated by the owner). Recipient keypair = suite.kem.deriveKeyPair(hkdfSha256(key, empty, "layers-disclosure/link/kem/v1", 32)); psk = hkdfSha256(key, empty, "layers-disclosure/link/psk/v1", 32); addrId from pk as above. Link = `https://<public app>/d#<keyHex>` (64 hex; no row id, so republishing does not break it). One format, one open path.

## 3. The drop (public validator)

Migration 21 "disclosure_drop" (validator/migrations.js, appended after version 20):
```
CREATE TABLE IF NOT EXISTS disclosure_drop (
  id TEXT PRIMARY KEY,          -- 32 hex, random, fresh per generation
  enc TEXT NOT NULL,            -- 64 hex
  ct TEXT NOT NULL,             -- exactly 4128 hex (fixed size)
  hint TEXT NOT NULL,           -- 4 hex (PRF under the recipient PSK)
  expires_hour INTEGER NOT NULL,-- hour index: floor(expiresAt / 3600000)
  del_hash TEXT NOT NULL        -- sha256(delete token)
) WITHOUT ROWID;                -- no arrival order at rest (anon.js discipline)
CREATE INDEX IF NOT EXISTS disclosure_drop_exp ON disclosure_drop(expires_hour);
```
down(): DROP TABLE. No anchor, fid, recipient, writer or mode column. `hint` is the one deliberate addition to the critic's column list; it is a PRF output, never recipient-identifying, and it is named in the posture (A-DROP-HINT-IS-A-PRF).

validator/disclosure.js `mountDisclosureDrop(app, db)` mounted in server.js after express.json() beside mountCaps (:162-163). Shapes: ID /^[0-9a-f]{32}$/, ENC /^[0-9a-f]{64}$/, CT /^[0-9a-f]{4128}$/, HINT /^[0-9a-f]{4}$/, HASH /^[0-9a-f]{64}$/, TOKEN /^[0-9a-f]{64}$/. MAX_LEASE_HOURS = 168. Config by name: DISCLOSURE_DROP_WRITE_TOKEN_SHA256 (64 hex; absent = unarmed), DISCLOSURE_DROP_MAX_ROWS (default 512), DISCLOSURE_DROP_WRITES_PER_HOUR (default 600, per token hash, in-memory bucket like caps.js:72-86).

- PUT /disclosure/drop — header x-layers-drop-token; body {id, enc, ct, hint, expiresHour, delHash}. 503 drop_unarmed (no hash configured); 401 (sha256(token) != configured, timingSafeEqual); 429 + Retry-After (per-token hourly cap); 400 (any shape, expiresHour <= nowHour, or > nowHour + 168); 409 (id exists: never overwrite); 413 drop_full (count >= MAX_ROWS); 201 {ok:true}. The device envelope headers are ignored on this route (the owner app's device is enrolled on the OWNER validator, not here).
- GET /disclosure/drop — no auth, no required header. Sweep expired, then `SELECT id, enc, ct, hint, expires_hour WHERE expires_hour > nowHour`, Fisher-Yates shuffle with crypto randomness, answer `{ armed: boolean, nowHour, count, rows: [{id, enc, ct, hint, expiresHour}] }`, Cache-Control: no-store. Nothing else is ever added to a row. Per-address token bucket already applies (server.js:134-155).
- DELETE /disclosure/drop/:id — header x-layers-drop-delete (64 hex). 400 shape; 403 when sha256(token) != row.del_hash; 200 {ok:true} on delete AND when the row is absent (idempotent; ids are public via GET, so absence is not an oracle).
- Sweep: `DELETE WHERE expires_hour < nowHour` on every GET and once a minute (custody.js:213-214 pattern).
- Logging: nothing per request; one aggregate line per minute, counts only (caps.js:34-42 style).
- Tests: validator/test/disclosure.test.js in `test:validator` (package.json:16), createApp(":memory:") like device.test.js:18-26.

Env contract: add "DISCLOSURE_DROP_WRITE_TOKEN" to MUST_NOT_SHIP in BOTH lib/platform/env-contract.ts:7-26 and validator/env-contract.js:4-18 (accept-cu4 asserts identity). The public validator legitimately holds only the SHA256 name, which is on no refuse list.

4c. Received store lib/disclosure/received.ts, namespace `receivedDisclosures` (ExtraNamespace, opaque padded record). Doc `{ records: { [addrId]: { seq, issuedAt, expiresAt, subjects, label, seenAt } }, lastFullFetchAt, lastTickOk, lastFetchError, malformed }`. `applyFetch(result, nowMs)` implements, in this order:
1. FULL iff HTTP 200, JSON parses, rows is an array, every row shape-valid (the §3 regexes), rows.length === count. Otherwise FAILED: lastTickOk=false, lastFetchError set, records untouched, nothing rendered until a later FULL fetch.
2. For each row × active address: compute the hint; on match, suite.open; parse; validate v===1, addrId === the address used, seq a safe integer >= 0, issuedAt <= now + 5 min, expiresAt > now, expiresAt - issuedAt <= 168 h, 1..8 subjects with fid 1..2^31, fname rule, display <= 48, kind in {main, persona}. Invalid → ignored and counted in `malformed`.
3. Monotonic seq per addrId: accept iff no record or seq > stored.seq; seq === stored.seq with identical content → seenAt refreshed; seq < stored.seq → ignored (a re-served older generation).
4. After all rows: a stored record whose addrId had NO openable envelope in this FULL fetch is DROPPED (revoked or not renewed). This is safe because the publisher PUTs the new generation before deleting the old (§5c).
5. Expired records are dropped at tick and at read.
6. The doc is sealed only when it changed (new seq, drop), through flushVault with chrome.ts:147-164's adopt-after-success rule; a failed vault write discards the tick's result (no ghost state) and is retried next tick.
Render predicate `disclosedForFid(fid)`: lastTickOk && record.seenAt === lastFullFetchAt && expiresAt > now → `{ label, subjects, addrId }`, else null. So: unknown (latest tick failed) = kept but not shown; missing from a full fetch = dropped; present = shown. Never a network call from this module.

5c. Publisher lib/disclosure/publisher.ts: `ensurePublisherLoop()` started from instrumentation.ts register() (nodejs runtime) when the §5a gate holds AND DISCLOSURE_DROP_URL + DISCLOSURE_DROP_WRITE_TOKEN are set (read by name at call time; boot line names only). A PUT failure leaves the old row live until its expiry and surfaces as lastError; a DELETE failure is retried each run and the row expires by itself. `revoke(grantId)`: revokedAt = now, DELETE current and previous immediately (visible as a write at click time — named A-DROP-REVOKE-IS-VISIBLE; a "quiet revoke at the next batch" toggle is v1.1), omitted from the next generation. Auto-renew: every live grant is re-sealed every run with expiresAt = now + leaseHours, so a 72 h lease survives up to 72 h of owner-service downtime and then lapses on the friend's side.

## 7. Tiers ("each tier gets a deeper version of you")

v1 data model: a grant = (friend address, subject list, lease). A tier = a named PRESET of subjects in `presets` (e.g. "Inner" = main + every public alt, "Close" = main + two alts, "Acquaintance" = main only is pointless and the UI says so). Choosing a preset snapshots its subjects into the grant; editing a preset re-snapshots every grant that references it on the next publish (seq+1). The ladder (tier k ⊇ tier k+1) is a UI hint, not enforced. Deferred, named as such in Help/docs: tiers governing private-post audiences across deployments (the same envelope could carry an audience key: v1.1), "this anon cast is mine" private reveals through the same envelope (v1.1, after the anon reveal addition closes its 3 reviews/4 sweeps), group management across the owner's devices, designated-verifier proofs of control per alt (v1.1, needs F25 KeyRegistry lookup), and the "blanked anon" view (see §8).

## 8. What plain Farcaster viewers see

Nothing changes on Farcaster: the subjects stay separate accounts; no cast, reaction, follow, profile field or onchain write carries the link; Neynar and the hubs are not called by this feature (0 credits). "Posts appear as blanked anon" is the anon account (the anoncast pattern, SECURITY-POSTURE §14.1/§20): posts the owner makes through it are the anon fid's posts for everyone, whitelisted or not; Layers cannot blank posts a plain client shows. Non-whitelisted Layers users see bare personas (resolver.ts:42-51), byte-identical to a stock client. A plain-Farcaster friend gets the /d card on the public site; nothing appears inside Warpcast or any client.

## 10. Privacy analysis

What each party learns. Public validator operator: that one token-authenticated writer exists; row counts in buckets of 4 and their hour-grained expiries; fixed-size ciphertext; the writer's batch times (hourly) and immediate revoke deletes; every reader's IP and tick times (every device fetches, so a fetch marks nobody as a friend); 4-hex hints that are pseudorandom without the PSK. Never: any fid, fname, persona id, anchor, which rows belong to whom, whether a reader holds an address, or the exact friend count. Owner service (the owner): its own data plus each friend's pk/psk (it can write to that friend until they re-pair). Friend's device: the subjects (fids, names), the owner's label, the lease; nothing about other friends. Farcaster/Neynar/hubs: nothing new. Public app server: `/d` path hits without the key (fragment), nothing else; the device talks to the validator directly.

Leak predicate "my hidden thing". Owner: "fid A and fid B are one person" exists only (a) inside ciphertext under a friend's key, (b) in the owner's sealed outboundDisclosures record, (c) in the friend's sealed receivedDisclosures record. It never appears in a DB column, a URL path, a log line, a request header, or a network fetch that names both accounts together (the badge draws from the envelope; the /d card prefetches nothing). The greps assert: no validator row joins two subject fids; no fname, persona id, anchor or token beside drop rows; namespace sizes are padded. Friend: "I am whitelisted by X" has no column, a uniform fetch, a sealed vault, and an IP indistinguishable from any visitor's.

## 11. Failure modes (never fail open)

Validator unreachable, non-200, malformed, count mismatch → tick FAILED → badges not rendered (unknown), nothing dropped, status visible in Settings › Show to a friend, retried next tick. receivedDisclosures unreadable or empty-but-sealed → throw like chrome.ts:89-113, render nothing, status says so. Vault write fails → doc rolled back, tick result discarded, retry. Envelope opens but is invalid → ignored, counted. Publisher PUT fails → old row stays live until its expiry, lastError shown, retry next run; DELETE of the old generation only after all new PUTs succeeded. Revoke DELETE fails → retried each run; the pane says the old note stays readable until <expiry> unless the delete goes through. 413 drop_full → loud in the pane, no silent skip. Token absent/invalid → publisher "unarmed", the pane names owner step H. Public deployment → outbound/publisher refuse at module entry; the env contract refuses the raw token at boot. /d → the three honest states in §4f. Clock skew → issuedAt > now + 5 min ignored; the server compares hour indexes only.

OWNER DECISIONS
- Where the drop lives: on the existing public validator (recommended: $0, no new service, the same operator) versus a separate tiny service. Default: the public validator.
- Publish cadence and lease: re-seal every 1 hour, leases of 72 hours that renew automatically (recommended; a 6-hour cadence would make a friend wait up to 6 hours after you share). Default: 1 h / 72 h.
- Who may publish in v1: only your owner service, with one write token (recommended). The cost: the public server can see that one writer exists and roughly how many notes it keeps, in groups of four. Open publishing for every visitor (with a per-window membership proof) is a later pass.
- Deniable by default (recommended): a note carries no signature, so a friend who leaks it leaks a claim, not proof. A transferable proof would be an explicit opt-in later; a proof only the friend can verify is v1.1.
- Who the grantee is: the friend's whole Layers identity (every persona of theirs sees the badge; recommended) versus one specific friend persona. Default: whole identity; compartment mode still hides it per persona view.
- Plain-Farcaster friends in v1 (recommended yes): they get a private link that opens a card on the public site; nothing appears inside their Farcaster app, and the link is only as private as the message that carried it (send it over Signal or in person).
- Revoking: immediate deletion at the moment you click (recommended; the public server sees a write at that moment) versus a quiet withdrawal at the next hourly batch. Default: immediate.
- Main account as a subject waits on Connect Main (the connector account, about $1, already your open decision). Recommended: build this pass now with persona subjects; your main joins the list automatically once connected. No new money is needed for this pass: $0 infrastructure, 0 Neynar credits.

RISKS
- Browser support for X25519 in WebCrypto: @hpke/core's X25519 is WebCrypto-backed; the device already ships it for rootlink/linking, but an older browser could lack it. Feature-detect at boot and fall back to @hpke/dhkem-x25519 1.8.0 (installed, unused) — not yet exercised in this tree.
- The badge has nothing to attach to on the public site until live reads are armed (FC-READ dormant since 2026-09-27) and the owner's accounts appear in discovery or are looked up by name; until then the feature is complete but visible only on test casts.
- Main cannot be a subject until Connect Main lands (connector fid, owner decision); v1 ships with persona subjects only.
- The hint column is a deliberate addition to the critic's column list; its security rests on HKDF under the PSK salted by a fresh enc. Review lens 1 must attack it (correlation across generations, distinguishability of dummies).
- A re-served deleted envelope stays valid until expiry; the lease (72 h) is the only bound. Shorter leases cost more publish traffic.
- Immediate revoke deletes are a click-time write the public operator can see; the quiet-revoke toggle is v1.1.
- The owner's vault holds every friend's PSK; an owner-service compromise (already A-PRODLIVE-THE-PASSPHRASE-IS-THE-ACCOUNT) lets an attacker write deniable notes to friends until they re-pair.
- Linked devices (no seed) cannot pair or read in v1; delivering inbox material through linkMaterial()/LinkedRoot is v1.1.
- The forced-tick dev action name in app/api/zk/route.ts (the one calling prefetchTick at :701) and the QR encoder's function name in lib/fc/connect.ts were located but not read in full; the builder must confirm both before wiring the suites.
- GET /disclosure/drop grows with the row cap (512 rows ≈ 2.2 MB worst case); the default owner footprint is a few KB per tick, but MAX_ROWS must not be raised casually on a deployment.
- Both SERVER_ONLY lists and both MUST_NOT_SHIP lists must stay byte-equal (accept-cu4 and the device fetch patch), and every new sealed namespace needs reset entries in boot.ts reloadIdentity and dev/route.ts resetSeed, or the root-mixing bug returns.
- Farcaster direct casts are not assumed end-to-end encrypted; a /d link sent by DC hands the note to that operator. The pane must steer to Signal or in person (VERIFY-YOURSELF).
