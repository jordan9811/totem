## 1. Scope

IN (v1, $0): ZIP/folder intake parsed in the browser page; parsed-only, sealed, chunked persistence with loud failures; the keyless nightly X-id→{fid, fname, X handle} index built on each validator and served whole; local matching + "N of the people you follow on X are on Farcaster" + one-click follow (owner service: real, budgeted; public: preview-kept + links); "X @handle, verified on Farcaster" read from the same index; the dated "from X" shelf with one-at-a-time re-post labelled "Originally on X, <date>"; the fingerprint warning; the honesty gate (fixture links relabelled, sync never "live", composer result shown, X destination hidden off-rig, Import-from-X settings row).
OUT (explicitly): anything needing the X API (OAuth link, bookmarks sync, crosspost, DM hook, login with X) — X2, owner-only, after a yes; the oEmbed "tweet-a-code" proof (terms unchecked); followers.js, DMs, media; bulk re-posting; auto-follow drip (v1.1, owner decision); the old attestation-based "deferred auto-follow" (kept rig-only for its suite, hidden elsewhere).

## 2. Where each step runs (the device/server split) and why

| Step | Public preview | Owner service | Why |
|---|---|---|---|
| Read the ZIP/folder, strip the YTD wrapper, drop PII | the browser PAGE (client component + fflate) | the owner's browser page, same component | the raw archive (hundreds of MB to GBs, with email/phone/DMs) is never uploaded anywhere; a multi-GB file cannot be POSTed |
| Persist parsed lanes (sealed, chunked) | the in-tab device → public validator | the owner app server → owner validator (private network) | the vault key lives in the device; whole-document sealing keeps names and values off the server |
| Build the X-verification index | public VALIDATOR job | owner VALIDATOR job | needs a long-lived process, SQLite for the fname mirror cursor, a file to serve and outbound crawl; the public app server is keyless/stateless; a browser must never crawl (398 pages per visitor would be both a load and a beacon) |
| Download the index + match | the in-tab device, WHOLE file | the owner app server process, whole file | the follow list never leaves the device; a whole-file download tells the server nothing about matches |
| Follow | preview only ("Keep", device-local) + profile links | real `followFc` through BUILD A's route, budgeted | the public preview holds no write key (MUST_NOT_SHIP) |
| "X @handle, verified on Farcaster" | not offered (public personas have no fid) | derived from the downloaded index for the persona's own/connected fid | no per-fid lookup beacon |
| Render the shelf | device (`ImportedView` via /api/profile, D-CU-0-4) | server (rig shape) | existing pattern |
| Re-post one tweet | refused (NETWORK_READ_ONLY) | Composer prefilled → write door (all BUILD A guards) | public posts only ever go through one door |

Rules: `/api/x/*` stays device-answered (no SERVER_ONLY change). The device reaches the validator at `VALIDATOR_URL` (deviceEnv) as persist.ts already does; CORS on the validator is already `*`. Nothing X-related ever reads `NEYNAR_READ_API_KEY`.

### G2 — Chunked sealed documents (lib/vault/chunkedDoc.ts)
A sealed document larger than one PUT, owned by a module, named per ROOT (never per persona: namespace names are visible to the validator per anchor, and per-persona names would hand it the sibling count).
- Constants: `CHUNK_PLAINTEXT_BYTES = 98304` (96 KiB plaintext → padded ≤ 97 KiB → sealed+base64 ≈ 135 KB < 256 KiB; a unit test seals a worst-case chunk and asserts the body size).
- `writeDoc(name, doc)`: `json = JSON.stringify(doc)`; split into n pieces; for i: `flushVault(\`${name}.g${gen}.${i}\`, sealWhole(ns, { _: piece }))`; then the manifest LAST: `flushVault(\`${name}.m\`, sealWhole(ns, { _: { v:1, gen, n, bytes, sha256, updatedAt } }))`; then empty the previous generation (`flushVault(\`${name}.g${prev}.${i}\`, {})` for each old i; failures here are logged, not fatal: stale chunks are unreferenced). A torn write leaves the old manifest pointing at intact old chunks.
- `readDoc<T>(name)`: read `.m` via `fetchState`; 404 → `{doc:null, loaded:true}` (genuinely empty); read the n chunks in parallel, verify count + sha256, decrypt via `unsealAny`, join, parse; ANY failure throws `"your X data could not be read (chunk 3 of 7 missing) — nothing was changed"` — never empty-as-success (the personaFid.ts rule). Module caches (`g.__layersXDocs`) hold `{doc, loaded, gen}`; `resetXDocsCache()` is called from app/api/dev resetSeed next to `resetPersonaFidCache` (route.ts:612) and from `resetState`.
- Widen `flushVault`/`fetchState` to accept `\`x${string}\`` names (a `ChunkNamespace` template type) rather than adding dynamic names to the `Namespace` union; `sealedNamespaces()` marks each chunk name as this device's sealed write (hydrate's plaintext-refusal rule applies to them on read).
- Write counts: a 20,000-post shelf ≈ 6 MB plaintext ≈ 65 chunks → ≤ 131 PUTs per commit, far under 2,000/device/hour.
- LAYERS_WORLD=empty: these docs are not `SERIALIZERS` namespaces, so hydrate does not partition them; every reader filters by `realPersonaIds()` under the flag (personas keyed `p_…` only), exactly as personaFid.ts does for its items.

### G4 — The keyless index: validator job + static file
- validator/xindex.js, started from createApp when `VALIDATOR_X_INDEX=on` (default off → the route answers 503 and the UI says "not available on this site yet"): first run 60 s after boot, then every `VALIDATOR_X_INDEX_EVERY_MS` (default 24 h ± 10% jitter). Migration (validator/migrations.js, next number): `x_fname_current(fid INTEGER PRIMARY KEY, username TEXT NOT NULL, transfer_id INTEGER NOT NULL)`, `x_index_cursor(key TEXT PRIMARY KEY, value TEXT NOT NULL)`.
- Crawl: `GET <source>/fc/account-verifications?platform=x&limit=1000&cursor=<next>` until `next` is absent or the page is empty; ≤ 2 requests/s; `User-Agent: layers-validator/x-index`; retry 429/5xx 3× honouring Retry-After; every row schema-checked (`fid` positive int, `platformId` /^\d{1,25}$/, `platformUsername` string ≤ 64, `verifiedAt` int); dedupe by fid+platformId. ANY failure aborts the run: the previous file keeps being served, `meta.lastError` records the page and reason, one log line with counts only. Expected: 398 pages, ~45 MB transfer, ~3.5 min.
- fname mirror: from `x_index_cursor.from_id`, `GET <fnames>/transfers?from_id=N` pages of 100, applied in id order: delete any row holding `username`; if `to !== 0` upsert `(to → username, id)`. Stop when a page has < 100 rows or after `VALIDATOR_X_INDEX_FNAME_PAGES_PER_RUN` (default 1,500 → the ~14,600-page backfill completes in ~10 nights; ~64 MB/night). Coverage ramps; rows without an fname carry an empty string and the UI copes.
- File `fc-index.v1.json.gz` in `VALIDATOR_X_INDEX_DIR` (default beside the DB), written tmp+rename, columnar: `{"v":1,"builtAt":"<iso>","rows":N,"fnameCoverage":0.93,"xid":"<comma-joined>","fid":"…","xu":"…","fn":"…","at":"…"}` (X usernames are `[A-Za-z0-9_]`, fnames `[a-z0-9.-]`: commas are safe). Meta `fc-index.v1.meta.json` `{v, builtAt, rows, bytes, sha256, fnameCoverage, fnameBackfillDone, lastError}`.
- Routes (mounted like /zk/anon-casts, unsigned, per-address rate limit applies): `GET /x/fc-index` → `Content-Type: application/json`, `Content-Encoding: gzip`, `ETag: "<sha256>"`, `Cache-Control: public, max-age=3600`, 304 on If-None-Match, 503 `{error:"index not built"}` when absent (never an empty index); `GET /x/fc-index/meta`; rig-only `POST /x/fc-index/build {sourceUrl, fnamesUrl}` (DEV_HOOKS; the suites point it at a local stub). `VALIDATOR_X_INDEX_SOURCE_URL` / `VALIDATOR_X_INDEX_FNAMES_URL` are local-only overrides, IGNORED on a hosted platform exactly like VALIDATOR_RL_CAPACITY (same `isHostedPlatform` guard, same warning line).
- Memory: ~400k rows transient in the validator process (~100 MB); the gate report records the measured RSS and file size; if the gzip exceeds 12 MB, v1.1 delta-encodes fids and drops `at`.
- Size truth: measured on page 0, 112 B/row of API JSON → ~45–55 B/row columnar → ~18–22 MB raw, est. 7–11 MB gzip. The owner can run `VALIDATOR_X_INDEX=on` on the laptop first to measure before deploying.

### G5 — Find my people: local matching, the panel, preview-keep, the owner follow queue
- `lib/x/indexClient.ts` (device process): `fetchIndex()` GETs `${validatorUrl()}/x/fc-index` with `If-None-Match` from the in-memory copy; parses columnar into typed arrays (fid Uint32Array) and string arrays; re-downloads when older than `X_INDEX_MAX_AGE_MS` (24 h) or on "Check again"; 503 → `{available:false, reason}`; a partial/aborted download never matches. Only the import page and the identity read trigger it (see A-X-2).
- `lib/x/follows.ts`: the `xFollows` doc `{v:1, byPersona:{[personaId]:{ids: string[], importedAt}}, matches:{[personaId]:{indexVersion, at, items: MatchItem[]}}, queue: QueueItem[]}`; MatchItem `{fid, fname, xHandle, verifiedAt, state: "new"|"kept"|"queued"|"followed"|"refused"|"failed"|"unconfirmed"|"own", note?}`; QueueItem `{personaId, fid, enqueuedAt}`. DECISION D-X-IDS-SEALED-NOT-HASHED: the X ids are stored RAW inside the sealed document (the old per-id hash protected a plaintext namespace that no longer exists; whole-document sealing hides names and values alike, and matching is then an O(1) set lookup instead of ~400k keyed hashes per re-match on a phone). The at-rest check stays: a raw X id, a tweet text or the archive email never appears in `adapter_state` plaintext. ## 5. Failure modes (never fail open)
| Condition | Behaviour |
|---|---|
| Index not built / 503 | panel: "The matching list isn't available on this site yet"; no count, no "0 matches"; identity badge absent |
| Crawl fails mid-way or a row fails the schema | the run aborts; the previous file is served; meta.lastError; one log line |
| Index older than 30 days | panel warns "the list is N days old"; matching still allowed |
| Download aborted | no match computed; the previous matches stay with their indexVersion |
| A chunk missing / sha mismatch / wrong key | readDoc throws; profile shelf says "couldn't be read: <reason>"; writes refuse until a successful read (`loaded`) |
| Flush 413 / network | PersistError with ns and KB; the wizard: "Couldn't save… nothing was kept. Try again" (retry is idempotent put-by-id); memory is not marked flushed |
| ZIP ≥ 4 GB, a wanted file > 512 MiB, posts over the cap | refused with the number and the folder/newest-N instruction; nothing partial is kept |
| Own fid among matches | `own`, counted, never actionable (the write door would refuse anyway: FC_SELF_LINK) |
| Follow: Neynar 4xx | `failed` + sentence, no automatic retry |
| Follow: timeout/5xx | `unconfirmed`, batch stops, "check in a Farcaster app"; never resent blindly |
| Daily budget hit | FC_CAP 429 sentence; the queue waits for a click tomorrow |
| Vault unreadable (persona records, docs) | routes answer 503 with the reason; nothing guessed |
| `markReposted` with an unknown hash | 409 |

## 6. Privacy analysis — what each party learns; the leak predicate
Things: F = the X follow list; M = the matched set; A = the X identity (handle/id); S = the shelf; P = which persona received the import; L = the persona↔X link. "My hidden thing" T is hidden from party X iff X's observations are identical whether or not T exists.
- Public validator operator: sees namespace NAMES per anchor (`xArchive.*`, `xShelf.*`, `xFollows.*`) and padded sizes → learns "this anchor imported an X archive" and a size CLASS of S and F (1 KiB steps; A-X-NAMESPACE-SIZE-CLASS); sees `GET /x/fc-index` per address and time → "this address opened Find my people" (A-X-INDEX-FETCH-IS-A-PAGE-VIEW; mitigated: only the import page fetches, at most daily); never F, M, A, S or P (ciphertext; per-root names).
- Public app server operator: the page view `/settings/import-x` (existing logging posture); no X data crosses the Next server on public (device-answered routes).
- Farcaster (api.farcaster.xyz, fnames): sees each validator's nightly crawl from one IP → "a Layers validator mirrors the list"; never any user. Snapchain is not used.
- The read relay (public, armed): a matched profile opened BY CLICK is a `user`/`user-casts` lookup logged per address (A-FCREAD-OPERATOR-SEES-READS); the LIST is never resolved through the relay (rule: no per-match lookups; A-X-NO-LIST-RESOLUTION).
- Neynar (owner service) and the whole Farcaster network: every real follow is public; over days the persona's follow set approaches F ∩ Farcaster, which fingerprints the persona as the X account's owner (A-X-FOLLOW-GRAPH-IS-A-FINGERPRINT: the warning, the persona choice, the budget slow it, they do not prevent it). A re-posted tweet links the persona to A by text (A-X-REPOST-LINKS-VOICE).
- x.com / farcaster.xyz: an external link opened by the user (A-X-EXTERNAL-LINKS-ARE-CLICKS).
- X: nothing (no API; the archive is read locally).
- Other visitors: nothing.
- Also stated: the archive is self-supplied and proves nothing about identity; only the Farcaster verification does (A-X-ARCHIVE-IS-SELF-SUPPLIED); the index source is a beta endpoint with unstated terms (A-X-INDEX-SOURCE-IS-BETA); page boundaries drift (A-X-INDEX-DRIFT); fname coverage ramps (A-X-FNAME-COVERAGE-RAMPS); D-X-IDS-SEALED-NOT-HASHED (§3 G5).

- A real follow set published over days fingerprints the persona as the X account's owner on the public network (A-X-FOLLOW-GRAPH-IS-A-FINGERPRINT); the warning and the 10-a-day budget slow it, they do not prevent it.
- manifest.js and the exact split-file naming were not confirmed by any source read today; the parser tolerates tweets/tweet and part files by glob, but the real archive may still surprise (VERIFY on the owner's archive).
- fflate stops at 4 GB (no ZIP64): archives over 4 GB must be extracted and picked as a folder; media-heavy accounts are affected.
- The fname registry backfill is ~14,600 pages of 100: coverage ramps over ~10 nights, so early match lists show 'fid N' for many rows; the ~/profiles/<fid> link is unverified.
- The verification list is ordered newest-first and paged by number, so page boundaries drift during a crawl; a nightly rebuild with dedupe is the mitigation, not a guarantee.
