SPEC
SIGN IN WITH FARCASTER (SIWF) ON THE PUBLIC SITE + PASSKEY-FIRST ONBOARDING: BUILD SPEC (read-only design, 2026-10-08, against the working tree at 8359c79 plus the uncommitted overnight builds)

VERDICT, FIRST
1. SIWF is IDENTITY, not CUSTODY. A Sign in with Farcaster proves "the human in this tab controls fid M right now" and binds M to the tab's root as a sealed vault record. It can never bring a lost identity back: SIWF yields no stable secret to derive a KEK from (docs/custody-model.md D-CU-0-7: every save method is a KEK source), and a fid-keyed method record on the validator would be a fid-to-anchor table the operator can read (fids are small integers, so hashing them hides nothing; that is exactly the "my hidden thing" leak). So the first-5-minutes order is: passkey first (custody), SIWF second (identity), 24 words advanced (escape hatch). The owner's pitch order "log in with Farcaster, generate a passkey, make your personas" survives, with the passkey offered at the first useful moment.
2. Verification runs ENTIRELY IN THE BROWSER DEVICE: the device creates the relay channel, shows the QR, polls the relay, parses and verifies the SIWE message locally, and checks fid-to-address on Optimism with one eth_call from the browser. The public app server receives nothing; a request for the route that reaches the server on a public deployment is refused 404 before the body is read. The validator learns one more sealed, padded, 1 KB namespace that EVERY device writes (uniform presence), never a fid.
3. Server-side verification (a "stateless verify" that issues nothing) is rejected on privacy grounds: it would hand the operator fid + address + time, joinable by address and time to the root's own signed validator traffic (SECURITY-POSTURE.md section 19, A-FCREAD-OPERATOR-SEES-READS shows the operator already joins reads to roots this way). Third parties (Farcaster's relay, the RPC provider) learn fid+IP but never the root; the operator must learn neither half.
4. Sign in with X is OUT of v1: X OAuth needs an X developer app with a card on file, pay-per-use, and a client secret held by a server (dx-x-interop.txt findings; the keyless public server cannot hold it). v1 is "Sign in with Farcaster" plus "Bring your X" (the archive, $0). The status rows say so.
5. Nothing in this pass touches the chain, adds a key to main, or spends: the requestFid/registrant findings of postconnect-results.txt do not arise, because SIWF writes nothing onchain. That is why it is the right v1 for strangers. Writes (posting as main from the public site) wait for the public write relay (notes/runbooks/GO-LIVE-FARCASTER.md section (h)), out of scope.

PROTOCOL FACTS, VERIFIED 2026-10-08 (cite list at the end)
- Library: @farcaster/auth-client 0.7.1 (npm; deps viem ^2.29.2, neverthrow). Relay default https://relay.farcaster.xyz, version path v1 (docs.farcaster.xyz auth-kit/client/introduction; http transport builds `${relay}/${version}/${path}`).
- Relay API (auth-client source): POST /v1/channel, JSON {siweUri, domain, nonce?, notBefore?, expirationTime?, requestId?, redirectUrl?, acceptAuthAddress?} -> {channelToken, url, nonce}. GET /v1/channel/status with header `Authorization: Bearer <channelToken>` -> {state: "pending"|"completed", nonce, url, message?, signature?, authMethod?: "custody"|"authAddress", fid?, username?, bio?, displayName?, pfpUrl?, verifications?, custody?, signatureParams{siweUri, domain, nonce, notBefore, expirationTime, requestId, redirectUrl}, metadata{ip, userAgent}, acceptAuthAddress}. A channel lives one hour on the relay (FIP-11). AuthKit polls every 1.5 s (useSignIn) / 1 s (watchStatus default) with a 300 s timeout, and verifies in the browser (useVerifySignInMessage), which is the precedent for a browser-side verifier.
- The SIWE message SIWF fixes (auth-client messages/build.ts + validate.ts): version "1", statement "Farcaster Auth" (legacy "Farcaster Connect" also accepted by the reference validator), chainId 10, exactly one resource matching /^farcaster:\/\/fid\/([1-9]\d*)\/?$/ (FIP-11's prose says farcaster://fids/<fid>; the implementation and the Farcaster app use farcaster://fid/N; accept the implementation form only), issuedAt set by the signer, nonce at least 8 alphanumeric characters.
- verifySignInMessage (auth-client messages/verify.ts): checks nonce and domain equal the expected values, verifies the signature with viem's verifySiweMessage, then (acceptAuthAddress default true) accepts the signer if isValidAuthAddress(signer, fid) OR getFid(signer) === fid. The viem connector (clients/ethereum/viemConnector.ts): getFid = IdRegistry.idOf(custody) at ID_REGISTRY_ADDRESS; isValidAuthAddress = KeyRegistry.keyDataOf(fid, padded authAddress) with keyType === 2 and state === 1; chain Optimism; publicClient over http(rpcUrl) or a fallback of several. Addresses, the same ones lib/fc/connect.ts already pins: IdRegistry 0x00000000Fc6c5F01Fc30151999387Bb99A9f489b, KeyRegistry 0x00000000Fc1237824fb747aBDE0FF18990E59b7e. VERIFY-YOURSELF at implementation: the exact byte encoding of the auth address key in keyDataOf (viem pad(address) to 32 bytes per the connector) by reading viemConnector.ts, which this read-only pass could only summarise.
- viem verifyHash (wevm/viem main): in the default mode it performs the ERC-6492 onchain eth_call FIRST and falls back to local ecrecover only when that call throws. So a browser verifier that wants no RPC round trip for plain custody signatures must call recoverMessageAddress itself for 65-byte signatures, and use the 6492 path (an eth_call) only for contract-wallet signatures (auth addresses can be smart accounts).
- Not applicable: Sign In With Neynar (no new connections after 2026-08-14, Neynar docs); Quick Auth (auth.farcaster.xyz JWTs) exists only inside Farcaster clients / mini apps (miniapps.farcaster.xyz); Neynar managed signers are the WRITE path (lib/fc/connect.ts, owner service), not a sign-in.

THE SPLIT: WHAT RUNS WHERE, AND WHY
Browser device (the public site; every page under app/(main) runs it, and it answers /api/* in the tab):
- lib/fc/siwf/*.ts (server-only modules bundled into public/device/device.js exactly like lib/fc/connect.ts is today) do the whole flow: channel create, QR, poll, verify, chain check, seal, persona mint.
- Network calls the device makes, through the UNPATCHED fetch (window.__layersOrigFetch, the way lib/adapters/neynar/content.ts reaches the relay), with credentials "omit" and referrerPolicy "no-referrer": (a) POST <relay>/v1/channel; (b) GET <relay>/v1/channel/status (Bearer); (c) POST <rpc> JSON-RPC eth_chainId once per session and eth_call for idOf / keyDataOf (and the ERC-6492 deployless call only for non-EOA signatures). Nothing to the Layers app server. One sealed PUT to the validator (the accountLinks namespace) through flushVault, signed like every other namespace.
- The route app/api/fc/siwf/route.ts is a DEVICE route (not in scripts/device-routes.mjs SERVER_ONLY), so the tab answers it in-process; on the rig (ZK_DEV_HOOKS=true, no owner secret) the server answers it with the fixture network, so the Playwright suites can drive it.
Public app server: holds nothing new, no new secret, no new must-not-ship name. The route's first line on the server: `if (typeof window === "undefined" && isPublicDeployment()) return 404 {error: "Sign in with Farcaster runs in your browser; this server does not verify sign-ins", code: "device_only"}` BEFORE any body is read (the /api/recovery precedent). deviceEnv.server.ts adds three hints to the page's device env (names only, never secrets): FC_SIWF ("off" hides the feature), FC_SIWF_RELAY_URL, FC_SIWF_RPC_URL.
Owner service: "na". The route refuses there with "Use Settings > Connect your Farcaster account on this service" (the owner's identity is server-held and the connect flow with a signer already exists).
Laptop rig: fixture mode (an in-process fake relay and fake chain, no request leaves the process), for the suites.

WHAT A SIGN-IN BINDS TO, AND WHAT IS WRITTEN WHERE
- Binds to: the visitor's ROOT (the device's keystore root). Not to the validator's roots row: the pseudo-fid row (lib/device/boot.ts pseudoFid) stays as it is. docs/custody-model.md D-CU-3-A-ROOT-WITHOUT-A-FID says a later binding "is a re-registration"; this pass explicitly does NOT re-register (a roots row with a real fid is a plaintext fid-to-anchor table) and amends that sentence.
- New vault namespace `accountLinks` (lib/vault/vault.ts VAULT_NAMESPACES, lib/adapters/mock/persist.ts ExtraNamespace), ONE opaque sealed record padded to 1 KB steps, read/written with the lib/identity/rootRoster.ts discipline (loadStrict with retries, a corrupted or deleted-but-pinned namespace refused, cache adopted only after a successful flush, lib/vault/sealedPins.ts markEverSealed). Shape: {v: 1, links: [{kind: "farcaster", fid: number, fname: string, displayName: string|null, pfpUrl: string|null, bio: string|null, personaId: string, authMethod: "custody"|"authAddress", signer: "0x…40hex", nonceHash: sha256 hex, messageHash: sha256 hex, verifiedAt: ms, verifier: {rpcHost: string}, disconnectedAt: ms|null}]}. NOT stored: the signature, the raw message, the relay's metadata.ip/userAgent, verifications, custody, the channel token. A signature is a transferable proof that fid M signed into this domain; keeping it widens what a vault compromise leaks for no product value.
- UNIFORM PRESENCE: lib/device/boot.ts bootIdentity step 5 seals an empty accountLinks record ({v:1, links: []}) for every freshly minted root (when the namespace 404s and this device never pinned it), so the namespace's existence on the validator carries no bit, and its padded size (1 KB) is the same with or without a link. New assumption A-SIWF-NAMESPACE-NAME-VISIBLE (the name is visible, the presence is uniform, the size is padded; A-CU-NAMESPACE-NAMES-VISIBLE applies).
- The persona: a KeystorePersona minted for main (lib/identity/keystore.ts createPersona), kind "public", a new field `publicSelf: true`, handle = the fname sanitised to [a-z0-9_] (dwr.eth -> dwr_eth; the fname itself is kept in the link record), name = displayName or fname, avatarUrl = pfpUrl when https, nonce deterministic `siwf-main/v1|<fid>` (a retried finish never mints twice), prefixed "fixture-siwf:" in fixture mode so a rig resetSeed purges it (keystore purgeFixtureConnectPersonas pattern). Recorded in rootRoster (recordPersona) and the sealed identityRoster (syncRoster), so the 24 words and a passkey unlock restore it. `publicSelf` also lands on RosterPersona and PersonaSummary (lib/adapters/types.ts) and on the store's Persona entry (lib/device/shims/session.ts adoptKeystorePersonas, lib/device/boot.ts).
- What it enables NOW on the public site: a read-only "public self": the switcher lists it with a "Farcaster · read-only" chip; its profile page /<handle> renders the sealed facts (name, @fname, pfp under the existing held-media rule, bio) with the "That's me" badge and, when the read relay is armed, a "Show my Farcaster posts" button that reads relayUser(fname) + relayUserCasts(fname) explicitly (never automatically; see privacy); Settings > Account shows "Farcaster: @fname (signed in) · Disconnect"; Help and the docs say what it is. The later "show my accounts to a friend" dead drop takes this record as its subject fid on the public site.
- What it does NOT enable: acting as it (the switcher row opens the profile instead of switching; /api/seed-persona refuses a publicSelf id on the public device with 403 PUBLIC_SELF_READ_ONLY, and the cast/react/follow/act-as routes refuse the same id belt-and-braces), forking FROM it (/api/identity/fork refuses: a fork carries a continuity proof to its source, which would publicly link the new persona to main), writes of any kind, recovery.
- One main per root; a tombstone on disconnect (disconnectedAt set, persona kept but shown "disconnected"); re-signing the same fid re-arms in place; a different fid is refused until the owner disconnects (exactly lib/fc/personaFid.ts recordConnectedFid's rules, minus the signer).
- Handle-stem rule both ways (CONNECT MAIN review PL-4): no other persona of this root may share a stem with main's fname (lib/identity/handleStem.ts derivedFromMain). Enforced at sign-in (an existing clashing persona refuses the sign-in with the rename sentence) and at persona creation / fork on the device (app/api/personas, app/api/identity/fork: today they skip the check when typeof window !== "undefined" because "the browser device never holds a main account"; now they consult accountLinks). Factor a shared `mainNameDerivation()` in lib/identity/mainName.ts that reads the connected record on the server and accountLinks in the device.

THE FLOW (app/api/fc/siwf/route.ts, one route, actions like /api/fc/connect)
GET -> {available, code?, reason?, mode: "live"|"fixture"|null, relayHost, rpcHost, link: {fid, fname, displayName, pfpUrl, personaId, handle, authMethod, verifiedAt, disconnected} | null, session: {id, stage, deadline, note, approval: {url, appLink, qr: {viewBox, path}} | null} | null}. Never the channel token, never a signature, never the message. No network call (status is a pure read of config + memory + the sealed record).
POST {action: "start"} ->
 1. gate: FC_SIWF not off; config valid; not a linked device (it holds no seed, so it cannot mint; sentence: "sign in on a device that holds your identity"); no live link to a different fid; relay URL is the default or loopback; RPC URL is the default or a bare https origin or loopback.
 2. nonce: 16 base62 chars from crypto.getRandomValues (never the relay's: the device must know it first).
 3. POST <relay>/v1/channel {siweUri: `${location.origin}/device`, domain: location.host, nonce, expirationTime: now + 10 min ISO, acceptAuthAddress: true}. Refuse unless the answer's nonce equals ours and `url` parses with an allowlisted host (farcaster.xyz, www.farcaster.xyz, client.farcaster.xyz, warpcast.com, www.warpcast.com) or the farcaster: scheme; VERIFY-YOURSELF the host the relay returns today on the first real run and widen the list only by a named constant. The session (token, nonce, deadline = min(10 min, the relay's hour), url) lives in process memory on globalThis, never persisted: an unsaved identity dies with the tab anyway, and a saved one simply starts again.
 4. answer GET with session.approval {url (for the QR and the phone button), appLink (the same url; no rewrite), qr: qrSvgPath(url)} (the QR encoder moves from lib/fc/connect.ts to lib/qr.ts; connect.ts re-exports).
POST {action: "poll", sessionId} -> one GET <relay>/v1/channel/status (Bearer). pending: unchanged. completed: VERIFY IMMEDIATELY, in this order, every failure a fixed code and nothing recorded:
 a. message and signature present and well-formed (signature 0x + 130 hex for EOA, else bytes); parse with viem/siwe parseSiweMessage.
 b. statement === "Farcaster Auth"; version "1"; chainId 10; domain === location.host (the one we sent); uri's origin === location.origin; nonce === ours (both the message's and the status's); exactly one farcaster://fid/N resource; N === status.fid; issuedAt within [now - 10 min, now + 2 min]; expirationTime (if present) in the future and not past our deadline; notBefore (if present) in the past.
 c. signature: if 65 bytes, viem recoverMessageAddress({message, signature}) must equal the message's address (case-insensitive) with NO RPC; otherwise (contract wallet) publicClient.verifyMessage over the RPC (ERC-6492 universal validator, deployless) must answer true. A thrown RPC error here is "could not check", retryable, never a pass.
 d. chain: eth_chainId must be 0xa (once per session); authMethod "custody": IdRegistry.idOf(address) === fid; authMethod "authAddress": KeyRegistry.keyDataOf(fid, key) returns keyType 2 and state 1; anything else refused. The RPC answer is decoded with viem decodeFunctionResult; an unreadable answer is "could not check" (retryable), never a pass.
 e. record: mint/resume the persona, recordPersona + syncRoster (loud), seal accountLinks (loud, flushVault). A failed seal keeps the verified result in memory so a retry seals without a new approval; a 409 from the validator re-reads first (never seal over a newer copy).
 f. stage "verified"; the answer carries the link and `moment: "signed-in"` so the UI can show the Save card when the identity is still tab-only.
 Refusals: stage "refused" with one of: siwf_relay (the relay did not answer), siwf_url (the sign-in link points somewhere unexpected), siwf_message (the signed message does not match this sign-in), siwf_signature (the signature does not verify), siwf_chain_unavailable (could not check the account on the blockchain; retryable), siwf_fid_mismatch (that signature does not belong to @name's account), siwf_one_main (another account is already your main here; disconnect first), siwf_handle_stem (rename persona @x first), siwf_linked_device, siwf_seal (verified but not saved; retry), siwf_expired. Every sentence is fixed text; no upstream text, no token, no signature, no address ever appears in an error (the lib/fc/readRelay.server.ts rule).
POST {action: "cancel", sessionId}; POST {action: "disconnect", confirm: "DISCONNECT"} (tombstone, persona kept and marked); POST {action: "fixtureApprove", sessionId, fid?, wrongSigner?, wrongFid?, badNonce?, badDomain?, expired?, authAddress?, unregisteredAuthAddress?, relayDown?, rpcDown?} rig-only (ZK_DEV_HOOKS=true and fixture mode; 403 everywhere else).
Polling from the card: every 1,500 ms while the tab is visible, one immediate poll on visibilitychange, stop at the deadline (10 min) with stage "expired". One step at a time per process (connect.ts `serialized`).

PRIVACY ANALYSIS (the leak predicate: can anyone compute root R <-> fid M?)
What each party learns from one sign-in:
- Farcaster's auth relay (relay.farcaster.xyz): the app domain and siweUri (so "Layers"), the nonce, the visitor's IP and user agent at channel creation and every poll (metadata), then the completed record: fid, username, display name, pfp, custody, verifications, the message and signature. Learns "fid M signed into Layers at T from IP X". Does not learn R, the personas, or anything the validator holds. Farcaster's own client sees the same minus the polls.
- The RPC provider (mainnet.optimism.io by default): "IP X asked idOf(custody of M) / keyDataOf(M, addr) at T". Same class of fact as the relay's, one more party. The device never sends it anything else.
- The Layers public app server: nothing (no request). The validator: one signed sealed PUT of a 1 KB namespace that every device writes anyway (uniform), from the device's address at T, exactly like any other write.
- The hosting platform: the device's validator write as before; no SIWF request path.
- The pfp host: when the avatar renders, "IP X loaded M's picture" with no referrer; mitigated by the existing held-media rule (CastCard mediaHostAllowed: off-allowlist hosts show the neutral disc until tapped), applied to the publicSelf avatar on the profile and the switcher.
- Other visitors: nothing. The link is ciphertext; the preview shows no cross-visitor data.
Residual channels, named as assumptions for SECURITY-POSTURE.md section 21: A-SIWF-COLLUSION-IP-TIME (the Layers operator plus the relay operator, or plus the RPC provider, can join IP X and time T to the root's signed validator traffic and learn R <-> M; the operator alone cannot); A-SIWF-OWN-PROFILE-READ (if the visitor presses "Show my Farcaster posts", the relay read of @fname from address X at T is joinable by the operator alone, A-FCREAD-OPERATOR-SEES-READS; so it is never automatic, the button says what it reveals, and the sealed facts render without it); A-SIWF-RELAY-TRUSTED-FOR-LIVENESS (the relay can withhold or delay a completed sign-in, never forge one: the signature and the chain check are what the device trusts); A-SIWF-NAMESPACE-NAME-VISIBLE; A-SIWF-PAGE-IS-THE-DEVICE (A-CU-5 restated: a same-origin script could start a sign-in; it cannot redirect the relay or RPC off loopback/default, and it gains nothing a page cannot already do); A-SIWF-PUBLIC-RPC-CORS-AND-LIMITS (unverified until the first real run: that mainnet.optimism.io answers browser eth_calls with CORS and at a usable rate; fail closed either way); A-SIWF-RELAY-CORS (AuthKit runs the same calls from browsers, so the relay answers CORS preflights for Authorization; unverified here). Also the existing A-CU-6-RP-ID-IS-THE-HOST becomes product-urgent under passkey-first (owner decision 5).
What the user is told, in the card before the first request: "Farcaster's sign-in relay will see that you signed in to Layers (and your address). Your browser then checks the account on the Optimism blockchain through <rpcHost>, which sees your address too. Layers' server sees nothing."

FAILURE MODES (never fail open; each is a fixed code + sentence, nothing recorded unless stated)

- 4. SIGN IN WITH X STAYS OUT OF V1: it needs an X developer app with a card on file, pay-per-use, and a secret only a server can hold. Money. Recommended default: out; v1 is Sign in with Farcaster plus Bring your X (the archive, $0), and the Help page and docs say so in those words.
- 5. THE APP'S DOMAIN BEFORE STRANGERS SAVE PASSKEYS: a passkey is bound to the host that saved it (A-CU-6-RP-ID-IS-THE-HOST), so passkey-first makes a later move to a custom domain orphan every saved passkey (the 24 words would still work). Money (about $10 to $15 a year for a domain; Railway custom domains are free) and product. Recommended default: decide now; if a custom domain is coming, add it before announcing the public site, and the Farcaster app's approval screen then shows that name instead of a railway.app subdomain.

RISKS
- VERIFY-YOURSELF on the first real run (cannot be verified read-only): the host in the relay's returned sign-in url today (farcaster.xyz vs warpcast.com vs client.farcaster.xyz; the device refuses any host outside its allowlist, so a wrong list blocks sign-in rather than opening anything), whether relay.farcaster.xyz answers browser CORS preflights for the Authorization header (AuthKit does the same calls from browsers, so expected yes), whether mainnet.optimism.io answers browser eth_calls with CORS and at a usable rate, whether the Farcaster app honours expirationTime, and the exact byte encoding of an auth address in KeyRegistry.keyDataOf (read viemConnector.ts when implementing; the harness's reference cross-check catches a mismatch).
- Collusion leak stated plainly: the Layers operator alone learns nothing, but the operator plus the relay operator (or plus the RPC provider) can join the visitor's address and time to the root's signed validator traffic and learn root-to-fid (A-SIWF-COLLUSION-IP-TIME). Only a network relay (OHTTP/Tor, label condition 1) closes it; this pass does not.
- Pressing 'Show my Farcaster posts' makes a relay read of the visitor's own fname from their address, which the operator alone can join to the root (A-FCREAD-OPERATOR-SEES-READS); it is never automatic and the button says what it reveals, but a visitor who presses it has told the operator who they probably are.
- SIWF is not recovery: a visitor who signs in and never saves loses the link with the tab (D-CU-0-6). The Save moment fires right after a verified sign-in; the copy must never imply that signing in saves anything.
- The device env is a page-settable global: the relay/RPC override rule (default or loopback only, no keyed provider URLs, nothing non-default on a hosted platform) is the whole defence against a same-origin script pointing a visitor at a rogue relay; the unit harness and P10 must stay in the sweep.
- viem's verifyMessage goes onchain first in its default mode; the verifier must recover EOA signatures locally and use the ERC-6492 path only for contract signatures, or every sign-in costs an extra RPC round trip and a flaky RPC becomes a sign-in failure. The fake RPC must implement (or deliberately fail) the 6492 deployless call so both branches are exercised.
- A user whose Farcaster account signs with a smart-contract auth address needs the 6492 eth_call AND keyDataOf; on an RPC that rate-limits browsers this path fails closed (retryable) and the card says so; it never falls back to trusting the relay's fid.
- Persona handle collisions: a visitor whose existing persona shares a stem with the fname is refused until they rename (PL-4 both ways); .eth fnames sanitise to underscores for the handle while the fname is kept separately; the profile route must resolve both.
- Suites that assert the old picker: accept-cu2 check 9 (save-passkey + save-social visible on the rig, the fixture 'Save with Farcaster' button) keeps passing only if the social fixture card stays visible on the rig and the Farcaster card does not steal the 'Save with Farcaster' button name; accept-help forbids em dashes and 'designed' on pitch rows; accept-cu6 forbids 'Read the docs' on the landing while the docs URL is unset; HelpPicture panels that name the old 'sign-in' id must be updated or check 3 fails.
- The unit harness adds @farcaster/auth-client 0.7.1 as a devDependency for the reference cross-check; it must never enter the device bundle (esbuild would bundle it if imported from lib/), and its viem peer range (^2.29.2) is satisfied by the repo's ^2.56.
- Two 'main account' representations now exist (personaFids connected records on the owner service, accountLinks on the public site); the write-relay pass must unify them behind one accessor before any write path reads the public one, and the show-to-a-friend pass must take its subject fid from accountLinks on the public site.
- Status honesty: the sign-in row may say 'live' only after the owner's real sign-in on the deployed site; the deployed smoke can assert the shape (server refusal, device status) but cannot exercise a real approval.
