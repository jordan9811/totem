## 1. Trust is a namespace glob over an open, first-come registry — the id, not the key, is honoured  — severity HIGH  — confidence: verified on code
**Where:** `lib/attest/subscriber.ts:13,27` (`DEFAULT_PATTERNS = ["onchain.*"]`), `lib/attest/ids.ts:40` (`issuerMatches`: prefix match), `validator/zk.js:852-874` (`POST /zk/issuers`: first key to claim an id owns it forever; no retire route; `ON CONFLICT DO UPDATE` never changes `pubkey`), `lib/attest/proven.ts` / `lib/zk/gate.ts:158` / `app/api/zk/route.ts` (`attested`, `attestedMap`, `issuers`) — every honour decision is `isHonoredIssuer(id)`.
**Attack:** (i) Squat: on any validator where the reference issuer has not yet registered (a `live` universe on first boot; a `fixture` universe after every `resetZk`, since registration is lazy — `lib/attest/registry.ts:41` signs at first issuance), anyone POSTs `/zk/issuers` with `id: "onchain.holdings"` under their own key. The legitimate module then gets 409 and `requestIssuance` refuses for everyone (`lib/attest/subject.ts`). The squatter issues `eth-gte-10` to any commitment it likes (see #2) and every subscriber on the default honours it by id. (ii) Sibling: even with the real family registered, `onchain.*` also honours `onchain.holdings-v2`, `onchain.kyc`, `onchain.wallet-age2` — any id anyone registers with `displayName` "Onchain facts — holdings" (free text ≤80). The `issuers` action returns `honored: true` for them; the rule builder takes `issuer/bucket` as free text. (iii) Operator-as-issuer: the prompt's "the operator is never the issuer" is a decision the interface does not enforce; the operator runs the validator and can register whatever id the default glob trusts. (iv) No rotation story: a leaked `.keystore/issuers/onchain.json` compromises all four ids at once (shared key, stated), and the compromised ids can never be retired — "rotation is a new id" means the OLD id keeps issuing, honoured by every default subscriber, indefinitely.
**What it learns / breaks:** forged bucket membership for any commitment under the honoured namespace; a subscriber's surfaces, audiences and the backpack's attested-tier score honour it. Under (iii), the operator becomes the honoured issuer of record and can pad any bucket at will — F5c with a signature on it.
**Fix or assumption:** honour by PIN, not pattern: `ATTEST_HONORED_ISSUERS` entries become `<id>@<pubkey-hex>` (the reference client ships the reference issuer's key; in this cohosted repo it can read it from `issuerKeyFor("onchain").pubHex`), `isHonoredIssuer(id, pubkey)` checks the registry row's key against the pin, and the `onchain.*` glob leaves the default. Add a signed retirement (`POST /zk/issuers/retire`, `retired_from_epoch`, optional `successor`) so `buildTrees` stops building a retired issuer's trees from the next epoch and `GET /zk/issuers` says so. Until then: **A-ATT-HONOUR-BY-ID** — trust is a first-come id on an open registry, the default glob honours the whole namespace, and a compromised or squatted id cannot be retired.

## 2. An issuance binds a wallet to a commitment nobody proved they control; one wallet vouches for unlimited commitments  — severity HIGH  — confidence: verified on code (the reach in a product topology is a hypothesis)
**Where:** `lib/attest/issuers/onchain.ts:228-262` (`issue`: verifies the wallet's EIP-191 signature over a challenge that names `subject.commitment`, never that the caller holds that commitment's identity secret; `retain` at :157 records the salted wallet hash but `issue` never consults it — no "this wallet already vouched for another commitment" check); `validator/zk.js:879-923` (`POST /zk/attest`: no device envelope, no root binding — `lib/zk/validatorClient.ts:270` `vpost` is a plain fetch; the comment in `lib/attest/subject.ts` calling the submission "identified, root-level like registration" is not what the code does: `register()` at `validator/zk.js:426` is anchor-signed, `/zk/attest` is not); commitments are public (`GET /zk/members?tree=valid`, `validator/zk.js:744`).
**Attack:** (a) Sybil the attribute: one wallet holding 10 ETH signs N challenges, each naming a different commitment (the attacker's N roots, or anyone's — the challenge is minted for any `{mode, commitment}` the issuer's API is handed); the issuer signs N `eth-gte-10` issuances; anyone POSTs them. Sold attestations, one whale, N "whales". (b) Pad a thin bucket past the floor with leaves that will never prove: 49 arbitrary commitments + 1 real subject clear `ZK_ANON_FLOOR`; the client's cohort check counts leaves, so the real subject proves into a bucket whose PROVING population is one — the presence log (`zk_attestation_claims`) then shows exactly which persona. This is F5c ("set contents are a trusted-validator property") done by a third party for the price of one qualifying wallet. (c) Tag a victim: attach any bucket to a victim's commitment; root-level, and the victim's device may then be offered to prove it. In this repo the only issuer client is the cohosted module whose route pins `zkCommitment()` (`app/api/zk/route.ts` `attestChallenge` / `requestIssuance`), so (a)-(c) need the issuer reachable as a service — the product topology §13 describes — or a second app instance; the absence of the check is verified, the reach is the hypothesis.
**What it learns / breaks:** the meaning of every onchain bucket ("the root controls a wallet that…") becomes "someone with such a wallet signed a string naming this commitment"; the floor can be met by furniture the attacker supplies, collapsing the proving set below it while every label reads green.
**Fix or assumption:** two checks in `issue()`: (1) proof of commitment control — the subject signs the same challenge with its Semaphore identity (`Identity.signMessage`; the issuer verifies with `Identity.verifySignature` and checks `commitment == poseidon(publicKey)`), so a challenge is dual-signed by wallet AND identity; (2) one wallet, one commitment — refuse (or revoke the earlier issuances of) a wallet hash already bound to a different commitment, with the re-issuance case (A-Z3-REISSUE: a root's new commitment legitimately re-binds its wallet) handled by revoking the old commitment's rows. The validator cannot do either (it must not learn wallets and the submission must stay unsigned); say so: **A-ATT-WALLET-REUSE** / **A-ATT-COMMITMENT-POSSESSION**.

## 3. The presence log plus thirteen public, root-level, 28-epoch-stable bucket trees is a cumulative intersection the budget does not bound and the fixture does not test  — severity HIGH  — confidence: verified on code (the population arithmetic is a hypothesis)
**Where:** `lib/zk/budget.ts:58-70` (`ZK_PROOF_BUDGET` default 2, keyed `mode:persona:EPOCH`; "epochs not bounded" is stated for tier partitions); `lib/zk/cohort.ts:63` (`checkCohort` is per `(mode, tree)` — no cross-tree, no cumulative check); `validator/zk.js:1005` (`GET /zk/attested-map`: every persona's `(issuer/bucket)` set; gated only when `LAYERS_REQUIRE_SIG=true`, otherwise public); `validator/zk.js:744,963` (every bucket tree's leaves and every commitment's full bucket profile are public); `scripts/accept-att4.mjs:251-271` (checks 2-3 intersect exactly the TWO buckets proved at ONE epoch, never a tier tree, never across epochs); `lib/attest/chain/fixture.ts` (`cohortFacts`: pairwise intersections engineered to ≈7N/12 by index).
**Attack:** the operator (or, unarmed, any peer) reads `zk_attestation_claims` each epoch and `zk_eligibility`. Bucket membership is root-level, public and stable for the issuance's life (28 epochs for three families); tier membership likewise. Persona P proves `{morpho, gt2y}` at E, `{eth-gte-1, votes-gte-1}` at E+1 (the budget resets per epoch), holds tier-4 for `foryou` at E+2. Candidate set = `morpho ∩ gt2y ∩ eth-gte-1 ∩ votes-gte-1 ∩ tier-4`, computed from signed placements the operator already has. No cohort rotation is needed (A-COHORT-ROTATION assumes the operator must ACT); the population's own structure does the narrowing, and nested buckets make the narrow ones (`gt4y`, `eth-gte-10`, `votes-gte-20`) the ones surfaces will gate on. Each bucket is ≥50 by the client's check; nothing checks the running intersection. In the fixture the by-index spread keeps pairs ≈70 of 120; in a real population `gt4y ∩ eth-gte-10 ∩ votes-gte-20` is a handful. Advertiser twin: `audienceSize` returns exact counts for any audience ≥ floor (`lib/adapters/mock/market.ts:110-116`), and `attest.holds neq` exists — two audiences differing by one clause reveal a below-floor set by subtraction; not new to this pass, but now over proven attributes.
**What it learns / breaks:** persona → root by intersection, without any of the machinery §13 treats as the threat (thin buckets, rotation). Persona-level, from the operator's own tables.
**Fix or assumption:** a CUMULATIVE cohort check on the client: per persona, keep the intersection of every tree it has proved into (the leaf sets are already on the device in `localPins` cohorts, tier trees included) and refuse a new partition when `|∩| < ZK_ANON_FLOOR`; and/or make the attestation budget per persona per ISSUANCE HORIZON (28 epochs), not per epoch. State it either way: **A-ATT-BUCKET-INTERSECTION** — the per-bucket floor is instantaneous and per tree; a persona's lifetime bucket set, intersected with its tier, is what the presence log hands the operator, and att4 tests one pair at one epoch under furniture built to pass.

## 4. A revocation is undone by replaying the original issuance within its two-epoch window  — severity MED  — confidence: verified on code
**Where:** `validator/zk.js:889-890` (`INSERT OR REPLACE … revoked_from_epoch NULL`), `:905` (accepts `issuedEpoch ∈ {epoch, epoch-1}`), `:917-919` (`prevActive` treats `revoked_from_epoch > epoch` as still active and keeps the old activation).
**Attack:** issuer signs at E (row: issued E, active E+1, expires E+1+V). Issuer revokes at E+1 → `revoked_from_epoch = E+2`. The subject (who holds the public part in its vault, `lib/attest/vault.ts`) re-POSTs the same signed part at E+1: `issuedEpoch = E = epoch-1` passes, expiry matches, signature verifies, `prevActive` is true (E+2 > E+1), and the row is REPLACED with `revoked_from_epoch = NULL`. The leaf never leaves. Revocation at E (→ E+1) is likewise undone with activation E+2. The window closes only once `issuedEpoch < epoch-1`, i.e. revocations made in the issue epoch or the next — the holdings family's entire 4-epoch life, the case an issuer most needs (a wallet sold or compromised right after issuance). No suite covers it: att1 #9 and att2 #8 revoke then check the leaf drops; att1 #9's "restore" is a fresh issuance, not a replay. A second, one-hour variant: a revocation's canonical has no nonce (`attestRevokeCanonical`, `issuedAt ± 1h`), so a revocation signed just before a legitimate re-issuance can be replayed against the new row.
**What it learns / breaks:** the issuer's revocation is advisory for two epochs; the posture's "the leaf drops at the next epoch" is false for a subject that keeps its public part.
**Fix or assumption:** never clear `revoked_from_epoch` on a replace unless `a.issuedEpoch > prev.issued_epoch` (a revocation is cleared only by a STRICTLY LATER signed issuance); simplest as `ON CONFLICT DO UPDATE SET … revoked_from_epoch = CASE WHEN excluded.issued_epoch > issued_epoch THEN NULL ELSE revoked_from_epoch END`. Keep a tombstone of the revoked `claim_hash` so that exact issuance can never re-enter. Give the revocation canonical the `claimHash` it targets.

## 5. Open registration + eager, per-leaf-signed tree builds + never-pruned placements is a cheap validator DoS  — severity MED  — confidence: verified on code
**Where:** `validator/zk.js:114` (`treesFor`: one tree per `(issuer, bucket)` with any row), `:313-393` (`buildTrees` builds and Ed25519-signs a placement per leaf for EVERY tree each epoch, in the 30-second warm timer and on every `/zk/trees`, `/zk/members`, `/zk/attest/buckets` request), `:852` (`POST /zk/issuers`: no cost, no cap, 64 buckets each), `:879` (500 rows per POST, no rate limit), no `DELETE FROM zk_placements` anywhere but the fixture reset; `lib/zk/prefetch.ts` fetches the full census every tick.
**Attack:** register M issuers (`x.a`, `x.b`, …), each with 64 buckets; enumerate `/zk/members?tree=valid`; POST issuances for every commitment into every bucket. Next epoch the validator builds 64·M Merkle trees over N leaves and signs 64·M·N placements, writes them forever, and the census payload the client prefetches every tick carries 64·M entries. Frozen-epoch reconstruction on restart repeats the work.
**What it learns / breaks:** availability — the tick, the warm timer and the client's prefetch; plus root-level graffiti (a single-leaf bucket is a public label on a commitment).
**Fix or assumption:** build attestation trees lazily on first request per epoch (still frozen once built), cap issuers per mode and rows per issuer, prune `zk_placements`/`zk_root_history` beyond the grace, and give registration a cost (PoW, as the anonymous channel already has). An operator allowlist of BUILT issuers would also work but hands the operator a veto over issuers — say which is chosen. **A-ATT-OPEN-REGISTRY-COST**.

## 6. The live issuer signs whatever Blockscout, Snapshot and an env-overridable RPC answer, and sends the wallet to seven third parties from the issuer host  — severity LOW  — confidence: verified on code
**Where:** `lib/attest/chain/live.ts:98,107,134` (address in the query string to three Blockscout hosts, POSTed to `hub.snapshot.org`, `eth_getBalance` to three RPCs whose URLs come from `ATTEST_RPC_*`); no response pinning, TLS only; `isError` ignored in `txlist` (a failed tx to a router counts as "interacted").
**Attack:** anyone who controls an `ATTEST_RPC_*` value, or sits on the path to a public indexer, feeds a balance or a transaction list; the issuer buckets it and signs. §13 admits under-reporting for the contract list only; over-reporting via the source is not stated. Separately, in this topology the issuer host is the user's host: the wallet address leaves the user's IP toward seven endpoints at issuance time.
**What it learns / breaks:** a forged bucket under the honoured key (soundness); the wallet ↔ user-IP ↔ issuance-time triple at third parties (privacy, cohosted only).
**Fix or assumption:** **A-ATT-FACTS-SOURCE-TRUST** (the issuer trusts its sources as-is; over-reporting is possible from the source side) and **A-ATT-ISSUER-EGRESS** (wallet addresses leave the issuer host in the clear to named third parties). Count `isError === "0"` only.

## 7. The issuer's retention file is a wallet → commitment link table; the salt sits beside the hashes  — severity LOW  — confidence: verified on code
**Where:** `lib/attest/issuers/onchain.ts:136-160` (`sha256("layers-attest-subject/1"|salt|address)` keyed to `{commitment, issuer, bucket, issuedEpoch}`, salt stored in the same JSON; a corrupt file silently yields a NEW salt at :146, orphaning every existing hash).
**Attack:** read the file (issuer-host compromise; the user's host here): hash the public address space with the salt and recover every wallet ↔ commitment pair — the salt only defeats precomputed tables. A corrupt file loses the issuer's ability to revoke by wallet without any error.
**What it learns / breaks:** §13's "keeps a salted hash… and nothing else" reads as if the link is not recoverable; it is, for whoever holds the file.
**Fix or assumption:** HMAC under the issuer key (or encrypt the file under it) and refuse to run on a corrupt file, as `issuerKey` already does for key material. Or state **A-ATT-ISSUER-RETAINS-LINK**.

## 8. The ninth label condition is computed only when the test rig asks; no product surface passes its bucket  — severity LOW  — confidence: verified on code
**Where:** `lib/zk/privacy.ts:64` takes `opts.attestation`; the only caller that passes it is `app/api/zk/route.ts:373` (`privacyConditions` action). `components/zk/PrivacyLabel.tsx:8`, `lib/zk/status.ts:131` and `app/(main)/settings/zk/page.tsx:12` call `privacyConditions()` bare. A mode with an `attest.holds` rule never hands its bucket to the label.
**Attack:** none direct — a thin bucket cannot be proved, so the surface is empty rather than leaky. But a "Morpho users" mode carries an eight-condition label that can read PRIVATE while its bucket is below the floor, which §13 says cannot happen ("carries a ninth label condition").
**Fix or assumption:** the feed/mode path collects the `attest.holds` buckets of the active rules and passes them (plural — a mode may gate on several) to `privacyConditions`; condition 9 fails if ANY is thin or un-honoured. Until then §13 should not claim the condition is on the surface.

## 9. Residue and smaller items  — severity INFO  — confidence: verified on code
- **Migration 009** (`validator/migrations.js` v9): scaffold rows land in bucket `any` with `claim_hash = ''` and signatures under the dead `layers-zk-attest/1` domain, for issuers that have NO `zk_issuers` row; `treesFor` still builds `attest:<old-id>/any` for them and `GET /zk/attestations` serves a non-hex `claimHash`. Harmless (dev-only rows, un-honoured), but a `DELETE` of the scaffold would be cleaner than carrying it. No `down` — stated.
- **`schemaHash`** is `sha256(JSON.stringify(schema))` on both sides after one JSON round trip; integer-like property names would be re-ordered by the parser and fail registration (fail-closed, self-DoS only). `displayName` is the one canonical field that may contain `|`; since the verifier rebuilds the string from fields rather than parsing it, no confusion is reachable.
- **Challenge:** `mintChallenge(id, subject, 0)` hard-codes epoch 0 (`onchain.ts:226`) — the challenge's epoch field is decorative. The challenge binds `(issuer, mode, commitment)` and not the wallet, so it is deliberately multi-wallet; fine. In-memory `pending` dies with the process (fail-closed); fine.
- **(d) timing:** `created_at`, `registered_at` are hour-grain; the batch delays activation; the proof rides the scheduled tick; the validator does not request-log (`validator/server.js:68` sets CORS only). The only issuance-time signal I can see is root-level: `active_from_epoch − issued_epoch ∈ {1, 2}` says whether the subject submitted in the issue epoch or the next. The cohosted issuer's `fetchEpoch` + `POST /zk/attest` + the vault flush of `zkAttestations` land together, but they name a commitment the validator already maps to the device. Nothing persona-level found.
- **(a)** No claim value or address reaches the validator on any path I traced; the exact facts die in `issue()`. The only routes by which a VALUE could travel are the ones in #6 (to third parties, not the validator) and a subject's own disclosure of its vault record, which carries `subjectCommitment` and so links the disclosed value to a public commitment — the subject's choice; worth one sentence in §13.

## Verdict

After this pass the operator — or, unarmed, any peer — can still resolve a persona to a root without rotating a single cohort or padding a single tree: the presence log names which buckets each persona proved, the buckets are public, root-level and stable for a month, the budget resets every epoch, and nothing on the client ever intersects the trees a persona has proved into (tier trees included); §13 admits thin buckets and A-COHORT-ROTATION admits an operator who ACTS, not a population whose own structure narrows a persona to one root. On soundness, §13 says trust is the subscriber's choice, but the subscriber chooses an id pattern on a first-come registry with no retirement, so a squatted, sibling, or compromised `onchain.*` id is honoured by default forever; the issuer binds wallets to commitments nobody proved they hold and lets one wallet vouch for any number of them, so the floor can be met by furniture and the proving set below it; and a revocation made in an issuance's first two epochs is undone by replaying the public part the subject already holds. None of these is stated; #1-#4 need code, #5-#8 can be assumptions with ids, and the migration residue is cosmetic.
